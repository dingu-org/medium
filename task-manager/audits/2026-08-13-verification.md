## Headline

Fifteen blocker/high claims went through adversarial verification: 9 CONFIRMED outright, 5 PARTIALLY_TRUE (real defect, inflated impact chain or wrong severity), 1 ALREADY_HANDLED as a recorded decision, 0 refuted. Of the six the original auditors self-labelled BLOCKER, three survive at that grade (safety escalation dying behind the conversation cap, the Embedded Signup v2 payload against Meta's 2026-10-15 cutoff, and the RLS/tenant-isolation suite that no automation ever runs); three were downgraded to high or medium. The recovered production-config pass then added two blockers no code audit could see — Vercel Production carries POK_ENV="staging", so the first real upgrade would create a checkout against POK's sandbox with live merchant credentials, and nobody can state whether the production database matches the code because the one checklist command meant to prove it (`pnpm db:migrate --env production`) is not a valid drizzle-kit invocation and silently migrates the local dev database instead. The independent security pass found no cross-tenant defect in the query layer — RLS is complete on all 23 tables, every server action derives ptId from the session, and a live 12-read/7-write attack probe returned nothing — but the admin surface authorizes on a self-asserted email while signup auto-confirms, so if klaididingu@gmail.com is not already registered in the production Supabase project, one anonymous signup yields every tenant's PII and a full payments CSV. So: the application logic is in better shape than the audit's severity labels implied, and the deployment is in worse shape. This is not weeks of feature work — it is twelve blockers, of which seven need only code (the largest is M) and five need Klaidi in a dashboard, plus a test suite that is currently red from a date fixture that expired on 2026-08-01 and that nothing but a human ever runs. The single hard deadline is Meta's 2026-10-15 Embedded Signup retirement, roughly nine weeks out, and it needs a live popup re-test on a real device after the change, so it cannot be the last thing done.

I also tested the two obvious mitigations and confirmed their state: changing an existing user's email via `PUT /auth/v1/user` does NOT take effect (GoTrue stores it in `new_email` and leaves `email` unchanged), and a second signup on a taken address returns 422 "User already registered" with no session. So the attack reduces to: register the ADMIN_EMAILS address first. Production is pre-launch with no onboarded PT, so whether that address is already an auth.users row there is unknown from the repo.

**Impact.** If the allowlisted address is not yet registered in the production Supabase project, any anonymous visitor can claim it with one signup and immediately read /admin (every PT's email, pt_id, per-PT AI cost in µUSD and Meta cost in µEUR, plan distribution, conversion metrics) and GET /admin/payments-export?all=1, a CSV of every tenant's email, pt_id, plan, period, amount and POK order id. That is a cross-tenant PII and commercial-data breach obtained without exploiting a single line of query code, and authorization currently rests on an attribute the identity provider hands out on request rather than on an immutable subject id.

**Fix.** Stop keying authorization on `user.email`. Allowlist immutable subject ids instead — `ADMIN_USER_IDS` compared against `user.id` — or keep the email check but additionally require `user.email_confirmed_at` and a server-side `pts.is_admin` (or equivalent) flag that only a migration can set. Either change is confined to `app/(dashboard)/admin/gate.ts` and its two callers. Separately, confirm out-of-band whether the hosted project has email confirmations enabled and whether the admin address is already registered.

#### [LOW] Unscoped message lookup on a client-controlled globally unique column

**Files:** `app/api/pwa/mutations/message/route.ts`, `lib/inngest/functions/appointment-events.ts`, `drizzle/migrations/0008_phase5_background_jobs.sql`

**Evidence.** The PWA send route writes `sourceEventId: input.clientMutationId` — a value chosen by the client — into `messages.source_event_id`, which carries the GLOBAL unique index `messages_source_event_id_uq` (0008, live-verified). The same column is also written by the internal pipeline with server-generated `events.id`. When the insert hits that index, `onConflictDoNothing()` swallows it and the recovery read is `tx.select({id: messages.id}).from(messages).where(eq(messages.sourceEventId, input.clientMutationId)).limit(1)` — no `pt_id` conjunct, unlike every sibling query in the same transaction, which all carry `eq(..., input.ptId)`. `lib/inngest/functions/appointment-events.ts:151` reads the same column the same way and then writes a Meta wamid onto whatever row it finds (`update messages set externalId where id = args.messageId`).

**Impact.** A tenant who supplies a `clientMutationId` colliding with another tenant's `source_event_id` gets that tenant's message UUID returned as `localMessageId`, has their own outbound message silently dropped from the DB while still being sent and billed on WhatsApp, and — on the appointment-events side — could have another tenant's wamid written onto their row, which per migration 0026's own note embeds the recipient's phone number. Exploitation requires guessing a v4 UUID, so this is a robustness and defense-in-depth defect rather than a live leak, but it is the one place a client-controlled identifier shares a globally unique namespace with server-generated ids and is read back without a tenant scope.

**Fix.** Add `eq(messages.ptId, input.ptId)` to the fallback select in the PWA route (and to the appointment-events lookup), so a collision resolves to `null` instead of a foreign row. Better still, stop overloading one column: give the PWA path its own `client_mutation_id` column on `messages` with a `(pt_id, client_mutation_id)` unique index, leaving `source_event_id` for server-generated event ids only.

#### [LOW] Push subscription upsert lets one tenant capture another's endpoint

**Files:** `app/(dashboard)/settings/push-actions.ts`, `drizzle/migrations/0015_phase9_push_subscription_unique.sql`, `lib/notifications/push.ts`

**Evidence.** `push_subscriptions_endpoint_uq` is a GLOBAL unique index on `endpoint` alone (0015, confirmed on the live DB), and `savePushSubscriptionImpl` upserts with `onConflictDoUpdate({ target: pushSubscriptions.endpoint, set: { ptId: user.id, keys, userAgent } })` — the conflict handler rewrites `pt_id` to the caller. There is no check that the row being taken over already belongs to the caller, and the action accepts any well-formed URL (`z.string().url()`) as the endpoint. `lib/notifications/push.ts` then fans out by `eq(pushSubscriptions.ptId, ptId)`, so ownership of the row fully determines which browser receives a tenant's notifications, and `dispatchPushForEvent` puts a patient's privacy-shortened name and appointment time into that payload.

**Impact.** A signed-in PT who learns another PT's push endpoint URL can rebind it to their own account. The victim silently stops receiving push notifications, and every notification generated for the attacker's tenancy — carrying a patient first name and appointment time — is delivered to the victim's device instead. The endpoint is a high-entropy secret issued by FCM/APNs and is not enumerable, so this is not practically exploitable today; it is a missing ownership check on a write that is allowed to change the tenant column of an existing row.

**Fix.** Make the conflict target `(pt_id, endpoint)` (add that unique index and drop or keep the endpoint-only one as a hygiene constraint), or keep the endpoint-only upsert but scope the update with a `where` on `pushSubscriptions.ptId = user.id` so a foreign row is never rebound — delete-then-insert is also acceptable since the browser re-subscribes anyway.

#### [LOW] No CSP, frame-ancestors, Referrer-Policy or nosniff headers

**Files:** `next.config.ts`, `middleware.ts`

**Evidence.** `next.config.ts` `headers()` returns exactly one header for `/:path*` — `Strict-Transport-Security`. There is no `Content-Security-Policy`, no `X-Frame-Options`/`frame-ancestors`, no `X-Content-Type-Options: nosniff`, no `Referrer-Policy`, and `middleware.ts` adds none either (it only refreshes the Supabase session). I checked the corresponding sinks and found the app itself clean — no `dangerouslySetInnerHTML` or `innerHTML` anywhere in app/, components/ or lib/, and no third-party script (the NEXT_PUBLIC_POSTHOG_* and SENTRY_* vars present in `.env.vercel.production` have no corresponding code) — so there is no XSS vector I could find today. What is missing is the second layer that keeps a future one from being fatal in a product holding patient conversations.

**Impact.** Session cookies are the whole authorization story for every Server Action and dashboard route, so any future script injection — a dependency compromise, a new rich-text surface, an admin page that renders untrusted content — escalates directly to full account and patient-data access with no CSP to contain it. Absent frame-ancestors, the dashboard is also framable, which puts one-tap destructive actions (cancel appointment, erase patient) within reach of a clickjacking overlay.

**Fix.** Extend the `headers()` block in `next.config.ts` with `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY` (plus `frame-ancestors 'none'`), and a CSP. Ship the CSP in `Content-Security-Policy-Report-Only` first since Next inlines bootstrap scripts; the nonce-based recipe in the Next.js docs, wired through `middleware.ts`, is the standard path to an enforcing policy.

#### [LOW] POK settle credits a period without checking the paid amount

**Files:** `lib/billing/payments.ts`

**Evidence.** `applyOrderOutcome` classifies the re-fetched order with `classifyPokStatus`, which returns 'paid' on `order.isCaptured` alone, and `settleOrder` then extends `plan_expires_at` by the full `row.period` and sets `plan='solo'`. The authoritative `order.amount` and `order.currencyCode` are read — `orderSnapshot()` persists both onto the ledger row — but they are never compared against the `billing_orders` row's own `amountMinor` / `currency`, which is what `createCheckout` derived from `plans.ts`. The module's own comment flags the adjacent uncertainty ("the ALL minor-unit factor is UNCONFIRMED"), so the amount contract with POK is known to be under-specified.

**Impact.** If POK's hosted payment page ever permits the payer to alter the amount, or a future POK API change lets an order be captured for less than it was created for, a tenant can buy a year of Solo for a token amount and the ledger will record the discrepancy without acting on it. This is revenue integrity rather than tenant isolation — no other tenant's data is reachable — but it is the one place where an externally supplied fact is trusted to grant an entitlement without being reconciled against the value we asked for.

**Fix.** In `settleOrder`, before extending the plan, assert `order.amount === row.amountMinor` and `order.currencyCode === row.currency`; on mismatch log at error with the order id and both values, leave the row in 'created' (or add a 'disputed' status) and return without extending, so the reconcile cron surfaces it instead of silently crediting.
