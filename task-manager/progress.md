## Decisions log

_Significant choices that diverge from the tech doc or that I want to remember the reasoning for. Newest first._

- **2026-08-23** — **The schema speaks the product's language: `pts` → `accounts`, `patients` → `customers` (migration `0031`).** Medium is horizontal (decision of 2026-08-14 above) but every table, FK and enum still said physiotherapy. **The name was fixed by one ruling from the owner: a business will always have exactly one login.** With login, business and tenant permanently one row, `accounts` names all three, and the objection that would otherwise have ruled it out — that "account" is the word you want for the _login_ side after a members split — does not apply, because that split was considered and rejected. `person`/`people` was the owner's first instinct and was argued down on one concrete point: both sides of a booking are people, so `appointments.person_id` beside `customer_id` carves nothing. `providers` collides with AI providers already in the tree, `workspaces` implies teams, `tenants` is infra jargon in UI code. `customers` over `clients` because a barber has customers. **Scope, all of it:** the 2 tables, 22 `pt_id` + 3 `patient_id` columns, `practice_name` → `name`, 27 FKs, 22 indexes, 2 RLS policy names, the `message_role`/`cancellation_actor` labels (`patient`→`customer`, `pt`→`account` via `ALTER TYPE … RENAME VALUE`, so stored rows stay valid), the `erasure_archive.scope` CHECK (rows moved, constraint swapped — it was `('patient','account')`, which after the rename would have read as two pointers at the same table), and `handle_new_user()`. The migration was generated from the live catalog rather than typed, and dry-run in a rolled-back transaction before it touched anything. **One real bug caught by the suite, worth recording:** the first draft of the trigger copied `0003`'s body; `0013` had silently _replaced_ that function to also seed the three service presets, so the draft would have left every new signup with an empty service list — 13 integration tests failed, the body is now `0013`'s with the new names, and every function body in the catalog was audited for stale references afterwards (only the one). Policy quals, index predicates and FK targets needed nothing: Postgres stores them as parse trees. Code: ~4,100 identifiers across 265 files, `lib/patients` → `lib/customers`, the snake_case data values, the scheduling prompt. **Deliberately untouched:** historical migrations, `task-manager/phases/*`, `docs/gdpr/dpa-template.md` (legal copy), ~350 `PT` mentions in comments and test names. **Still open — a wording decision, not a sweep:** Albanian user-facing copy still says `pacient`/`fizioterapist` (~105 sites: `lib/i18n/dict/*`, legal pages, landing, `lib/ai/prompt.ts`, `app/layout.tsx`, seeds). `pacient → klient` is obvious; what replaces `fizioterapist` is positioning. Verified: `db:generate` reports no schema changes against the hand-derived `0031` snapshot; typecheck, lint, unit 68/682, integration 65/653; applied to local, preview and production (preview was at 0030, production at 0027 so it also took 0028–0030) — both verified afterwards at 32 migrations, zero stale object names, the one existing account row and its 3 services intact, ACLs unchanged.
- **2026-08-14** — **One shared definition of an affirmative: the offer and the reminder now mean the same thing by "yes".** The precedence rule the entry below records only decides messages _both_ subsystems could claim, and the two did not agree on what they could claim: `lib/reminders/parse-response.ts` accepted `konfirmo`/`dakord`/`po`/`ok`/`okay` and `po` plus one word, while `isHandoffAcceptance` demanded exact equality with PO. Everything in that gap skipped `resolveInboundClaim` entirely and went to whoever runs first, which is always the reminder. Measured by the verifier: with the offer as the newer question by 85 minutes, `"po faleminderit"` confirmed the appointment, nothing escalated, and the patient's question was dropped — the same silent failure, one spelling narrower. **The owner's call (2026-08-14): remove the asymmetry rather than special-case it.** The parser moved verbatim to `lib/language/reply-intent.ts` (`parseReplyIntent` + `isAffirmative`), which both subsystems now read; `isHandoffAcceptance` is a one-line call to `isAffirmative`, so the timestamp rule decides the winner instead of a spelling technicality. Every hard-won guard came with it: the ambiguous-particle length gate, the explicit-command precedence that keeps "Ok, anuloj" a cancellation, and above all the progressive-particle bound — Albanian `po` also heads an ordinary statement, so `"Po pyesja për oraret"` ("I was asking about the hours") is a yes for nobody and still reaches the model. The folding was unified in the same move: `handoff-offer.ts`'s NFD/diacritic fold now lives in the tokeniser, so `Pò` and a decomposed `ë` resolve like their plain forms, and both apostrophes fall out of the letters-and-digits character class (`s'ndal` = `s’ndal`). **The accepted risk, stated rather than hidden:** a casual `ok` can now accept an outstanding offer. The bound is judged sufficient — an offer is armed against the patient message it answered and `handoffOfferOutcome` accepts _only_ the message directly after it, so `ok` is read as acceptance in exactly the one position where `ok` is answering the offer; being wrong there escalates to the PT, who sees the patient's real question, which is recoverable and the safe direction, against an old failure that silently mutated a booking. The offer copy still asks for the single word PO and must keep doing so — one clear instruction is the UX; accepting the natural variations as well is the fix. Ablation-proved both ways: restoring exact equality fails the new tests (11 unit, 9 integration), and a naive "leading po" acceptance fails the progressive-particle guards at engine and inbound level. Verified: typecheck, lint, unit 68 files/682 tests, integration 65 files/653 tests (+37/+11 over the previous checkpoint); no migration.
- **2026-08-14** — **The "PO" collision: with a reminder and a handoff offer both outstanding, whichever question was asked most recently wins.** This closes the known gap the handoff-offer entry below left open, after the verifier proved it end to end: `lib/reminders/parse-response.ts` reads `po` as an appointment confirmation, and PO is also exactly the word the handoff offer asks for. `handle-inbound-message` runs the reminder handler ahead of the engine and returns as soon as it produces an outbound, so a bare "PO" with both outstanding confirmed the appointment and the accepted handoff silently never happened — the patient was answered about something they had not asked about, and the question they wanted passed to a person was dropped with no trace. **The rule is the owner's call (2026-08-14): the most recently asked question wins.** Neither subsystem can be the fixed winner, because both orderings genuinely occur — a scheduled reminder lands after an offer, an offer is made after a reminder — so any static precedence is wrong about half the time; recency is also how a person reads a one-word reply: it answers the last thing asked. Mechanism: `resolveInboundClaim` (`lib/inngest/functions/handle-inbound-message.ts`), a `resolve-turn-precedence` step **ahead of the reminder step, never inside it** — once `handleReminderResponse` has claimed the message the run is over and the engine, and with it the acceptance, is unreachable. The offer is dated by the `created_at` of the patient message its anchor points at (`outstandingHandoffOffer` now returns `offeredAt`); the reminder by the `sent_at` of the very candidate the response handler would act on (new `pendingReminderSentAt`, running the same `chooseCandidate` selection — not "any reminder exists"). **Only a message both sides could claim is weighed at all**: the offer can claim exactly what `handoffOfferOutcome` accepts — the acceptance word, as the message immediately after the offer — so ANULO/RICAKTO and every other deterministic reminder path are untouched, and a conversation with no armed anchor pays nothing here. **The tie-break is strict `>`, and the tie is reachable, not theoretical**: the offer wins only when strictly newer, so an exact tie goes to the reminder — Postgres keeps both instants to the microsecond while a JS `Date` truncates to the millisecond, so an offer made within 999µs of the reminder compares equal here. The reminder is the safer side of that coin: confirming an appointment the patient does hold is recoverable, and the offer is re-made the moment they ask again. A dedicated tie test (`73e4ee7`) pins the comparison, because a loosening to `>=` would silently move a tied turn from a confirmation to an escalation and nothing else would notice. When the reminder wins **the offer lapses with it** — the gate clears the anchor — consistent with only-the-immediately-next-message-accepts: the patient answered the reminder, not the offer, and an anchor left armed against some later unrelated message is exactly the loose acceptance the design refuses. **Fixed in the same wave, verifier-found: acceptance is now escalate-first, transactionally** (`6e45eab`). The acceptance path cleared `handoff_offer_message_id` and only then called `escalateToHuman`, in two separate statements; the anchor is the only record that an acceptance is owed, so a crash in that gap lost the handoff for good — the retry found no anchor, fell through to an ordinary turn, and the patient who had said PO was never passed to a human: the identical silent failure the precedence gate exists to prevent. `acceptHandoffOffer` (`lib/conversation/engine.ts`) now escalates first, durably, before anything consumes the anchor — a crash anywhere after it leaves a retry that escalates again, idempotently, since the second call finds the conversation already human-owned — and the clear rides in the reply's transaction, so the remaining gap (anchor gone, promise unsent) cannot open either. The read is split from the write on purpose: `handoffOfferOutcome` decides, `clearHandoffOffer` disarms, and only a lapse still clears at the top of the turn. **Two unintended consequences, found by a verifier after the fact and recorded as what they are — behaviour changes nobody chose, standing as accepted debts:** (1) the precedence gate runs before the takeover check, and during a PT takeover the reminder handler deliberately still runs (2026-06-17 decision), so a bare PO that a newer offer out-claims is now routed toward an engine the takeover then skips as `conversation_inactive` — the deterministic reminder confirmation a takeover previously produced is suppressed, and the PO does nothing beyond the manual-reply nudge; (2) the collision tests in `handle-inbound-message.integration.test.ts` **mirror the Inngest body rather than executing it** — their own comment says so — re-running gate → reminder step → engine in test code, so they prove each part and the rule but would pass unchanged if the real handler wired the gate after the reminder step or not at all; the assembly itself is untested. Verified at the fix wave's head (`794d61b`..`73e4ee7`): typecheck, lint, unit 68 files/645 tests, integration 65 files/642 (+2/+7 over the Wave 1 checkpoint); no new migration — the anchor column is `0029`, unchanged.

- **2026-08-14** — **Non-text inbounds are persisted, not dropped; and at the monthly cap the professional is told.** Two silences fixed, both first-week-of-real-use bugs. **(A) Non-text.** A voice note, photo, document or sticker used to leave no `messages` row at all, so the patient got no reply _and_ the professional never saw it: the unread badge, the chat-list preview and the realtime refresh all read that one row. The webhook now writes it inside the transaction it already opened, with a deterministic Albanian placeholder for content (`[mesazh zanor]`, `[foto]`, …) plus the caption when there is one — captions ride on the media object, never on `msg.text`, so the patient's own words were being dropped too. `messages_external_id_uq` + `onConflictDoNothing` gives that branch the redelivery dedupe its own comment said it lacked, and `bumpLastInboundAt` keeps taking the inbound's own timestamp, untouched, so a redelivered two-day-old image still cannot re-open an expired service window. **The placeholder is never handed to the model** — it is our text, not the patient's, and a model asked to answer `[mesazh zanor]` would invent what the voice note said; the `message.received` event carries `nonText: true` and the inbound job branches before the engine. The reply is one fixed sentence that says the assistant reads text, and it **carries the same handoff offer** as any out-of-scope question (same acceptance word, same anchor, same `businessLabel`), because "I cannot read this" is exactly when a person should take over if the patient wants one. **Three judgment calls.** (1) The throttle is **one notice per conversation per local day**, modelled on `prepareCapHandoff` — not once per conversation ever, as literally briefed: a conversation row lives as long as the patient does, so a once-ever notice would meet the voice note they send three months from now with the very silence this exists to remove. (2) The placeholder map (`lib/conversation/non-text.ts`) **replaces** the route's separate `PATIENT_CONTENT_MESSAGE_TYPES` allowlist rather than sitting beside it: two lists that must agree, don't. A type is added in one place and cannot end up persisted without a placeholder; anything absent (`reaction`, `system`, `request_welcome`, `unsupported`) is still ignored outright. (3) The identical idempotent "fixed-text AI reply" insert now existed twice and was about to exist three times, so it moved to `lib/conversation/deterministic-reply.ts`, which also pins `provider:'internal'` and zero tokens/cost in one place — a fixed sentence that reported tokens would inflate the cost dashboard. **(B) The cap.** At the monthly conversation cap the patient got a holding message, the professional got **nothing**, and the thread still looked AI-handled. Worse, the gate compensates its day-fact away when it turns a patient away, so the 2nd..Nth message of a capped day hit the cap afresh, the once-a-day handoff throttle returned `skip`, and those messages produced **silence for everyone**. `handOffCappedConversation` now hands the thread over and pushes. **No offer is made** — at the cap the assistant genuinely cannot serve this patient, so there is nothing to offer and nothing to ask. The flag is the ordinary human-handoff pair (`ai_active=false`, `escalation_state='requested'`) and not a cap-specific state: the inbox, the chat banner and the Today list all already read that pair, and a third value they would treat identically buys nothing. The push is deliberately `conversation.needs_reply` ("Mesazh i ri") and **not** `conversation.escalated` ("X asked to talk to you"): at the cap the patient asked for nothing. The known cost of that choice, accepted: `offer-resume` is armed by `conversation.escalated`/`conversation.taken_over`, so a capped thread gets no automatic resume offer — which is honest, since while the professional is at their cap the assistant would only hit it again on the next message, and handing the thread back from the chat screen clears the flag exactly as it does for any escalation.

- **2026-08-14** — **The handoff offer: the replacement for the deleted detector, and the second half of the same decision.** The assistant no longer classifies anything. When the model judges a request to be outside what it can do — anything that is not booking, rescheduling, cancelling, or answering about the configured services and availability — it calls the new `offer_human_handoff` tool and the engine answers with **one static, vertical-agnostic sentence**: _"Mund të ndihmoj vetëm me takimet. Nëse dëshironi t'ia kaloj këtë pyetje {biznesi}, përgjigjuni me PO."_ One sentence for every case there is, with no emergency guidance in it, deliberately: the product schedules appointments for barbers and nail salons as well as physiotherapists, and it is not designed to handle emergencies. **The model is the only judge of scope; nothing reads the patient's words before it.** The tool is a pure signal — it changes no conversation state, because offering is not escalating. **The one design point that carries real risk is the scope of acceptance, and it is the reason for the shape of the state.** `PO` is Albanian for "yes" and is exactly what a patient types to take a proposed time slot, so a loose rule would turn every slot confirmation into a permanent handoff — the same class of bug as the deleted detector's "E marta nuk funksionon". Acceptance is therefore bounded twice over: the match is **whole-message** (folded case- and diacritic-insensitively, the one part of the deleted `safety.ts` worth keeping), and **only the message immediately after the offer can be it**. That bound is enforced by anchoring the offer to the patient message it answered — `conversations.handoff_offer_message_id`, migration `0029_handoff_offer_anchor`, a plain uuid and deliberately not an FK (retention purges messages, and a dangling anchor simply stops matching, which is a lapse) — and accepting only when that message is still the patient's most recent one before the incoming message. **An anchor rather than a boolean flag on purpose**: an offer then lapses by itself, and no other code path has to remember to clear it — a globally paused assistant, a capped conversation and a PT takeover all leave the anchor stranded, and stranded is correctly read as lapsed. The offer message and its anchor commit in one transaction, in that order, because an armed offer whose message never reached the patient is precisely the bug that would make an ordinary "po" escalate a conversation nobody offered anything to. On acceptance the engine escalates through the existing `escalate_to_human` path — unchanged behaviour, new trigger — escalation first and the confirmation reply second, so a crash cannot leave a promise made and unkept. **Three judgment calls beyond the literal instruction, all deliberate.** (1) The acceptance sends a second static sentence (_"Patjetër. Këtë bisedë ia kalova …"_, the wording of the deleted `human_requested` copy): the design says the assistant goes silent, but silence in answer to "PO" reads as a failure, and every other handoff path in the product says something. (2) The prompt's `- If urgent symptoms are mentioned, do not continue scheduling in the same turn. Escalate.` bullet is **removed**, not left: it is a second, contradictory rule for an input the new scope rule already covers, and an emergency-triage instruction is exactly what the 2026-08-14 product decision took out. `prompt.test.ts` now asserts the prompt contains no `urgent symptoms|emergency services|ambulance` at all — the tripwire against it coming back. (3) The failed-turn handoff's English fallback `'the physical therapy practice'` is replaced by the shared vertical-neutral `businessLabel()` (`'biznesit'`): it named a discipline in a horizontal product _and_ rendered a stray English noun phrase inside an Albanian sentence. Verified: typecheck, lint, unit 67 files/629 tests (+1 file, +22), integration 64 files/623 tests (+6), `0029` applied to the local DB and `pnpm db:generate` reports no residual drift. **Known gap, not fixed here:** `handle-inbound-message` runs the reminder-response handler before the AI turn, so if an offer is outstanding _and_ an unanswered reminder exists for an upcoming appointment, a bare "PO" is read as confirming the appointment and never reaches the engine. Narrow, and resolving the precedence is a separate decision.

- **2026-08-05** — **Reasoning effort removed from every environment: a thinking budget cannot fit inside `maxOutputTokens: 500`.** Production threw `ConversationEngineError: Model returned no patient-facing text` on live `message.received` runs. Cause: OpenRouter does not take `reasoning: {effort}` as a standalone knob — it _derives_ the thinking budget from the same request's `max_tokens`, as `max(min(max_tokens × ratio, 128000), 1024)` with ratio 0.2/0.5/0.8 for low/medium/high, and documents that `max_tokens` must be strictly higher than the resulting budget so the reply has somewhere to go. At the engine's `maxOutputTokens: 500` that computes to `max(400, 1024)` = **1024 — larger than the entire 500-token allowance**. Thinking consumed it all, the model returned empty text, and `runModelTurn` fell to its `empty_response` throw; `empty_response` is retryable, so all three Inngest attempts failed identically and the patient got the `handoffFailedTurn` technical-failure message with the thread escalated. **The 1024 floor is the part worth remembering: below `max_tokens` 5120 every effort level collapses onto it, so dropping `high` → `low` fixes nothing.** Effort is workload-gated (a simple booking turn emits 0 reasoning tokens even at `high`), which is exactly why this was intermittent rather than total, and why it survived the cutover's live probes — those measured that effort _worked_, on prompts and a token budget that happened not to collide. Regression window is precise: `b5c24b9` unset `OPENROUTER_PROD_MODEL`, which is what first put `reasoning` on the wire at all (`selectModelForPlan` had returned `reasoningEffort: undefined` for any env-selected model), and `3c5a9c6` then extended the same `'high'` to dev/preview. Fix chosen over raising `maxOutputTokens` to ~2000: the cutover's own measurement says ordinary booking turns think 0 tokens, so `high` was buying close to nothing on the real workload, while the 500-token ceiling is doing real work as a WhatsApp reply-length and cost control — trading it away to rescue a feature with no measured benefit is the wrong side of the trade. `PlanModelConfig.reasoningEffort` is now optional and carries the constraint in its doc comment; `lib/ai/client.ts` already omitted `reasoning` when falsy, so the request shape returns byte-identical to pre-`b5c24b9`. `ai.turn_completed` gained `reasoningTokens` + `finishReason`, whose absence is precisely why this had to be diagnosed from a reconstructed request body rather than from the production logs (which showed only `tokensOut: [REDACTED]`). Regression tests assert **no** `reasoning` key in all three environments. Residual risk accepted, not closed: `BILLING_PLAN_OVERRIDES` can still reintroduce the pairing at runtime, and nothing asserts `maxOutputTokens` > the derived budget — a load-time guard in the `assertProductionPrivacy` mould was considered and deliberately not built. typecheck + lint clean; unit 66 files/637 tests pass; integration 63/64 files pass (the same 8 pre-existing `sendUpcomingReminderTemplate` failures, re-verified against a clean stash baseline — unchanged and unrelated).
