## Decisions log

_Significant choices that diverge from the tech doc or that I want to remember the reasoning for. Newest first._

- **2026-06-12** — Phase 5 background jobs use durable DB event/outbox writes for inbound WhatsApp, connection-created, and revocation producers, followed by an immediate publish attempt; the one-minute outbox publisher remains the recovery path. Appointment subscribers always create an additional idempotent patient confirmation keyed by source event. Reminder scheduling uses Inngest `cancelOn` keyed by appointment id, one `reminder_jobs` row per appointment, a 5-minute delay for 2–24 h short notice, and skips appointments under 2 h notice. AI-provider circuit breaking is deferred to Phase 11.
- **2026-06-12** — Phase 4 implementation plan: reschedules update the existing appointment row and preserve its active status; pending appointments may transition to completed/no-show; v1 uses fixed 60-minute appointments with no buffer; active overlaps are prevented by a Postgres exclusion constraint; appointment events use an append-only event log plus a durable outbox with idempotent Inngest event IDs.
- **2026-06-10** — Phase 3 review hardening: patient-controlled WhatsApp profile names no longer enter the system prompt; the prompt now includes both UTC ISO and explicit practice-local time, with invalid IANA timezones failing rather than silently using UTC. Safety patterns retain conservative escalation while avoiding obvious fall/coverage false positives, and equal-timestamp history has a stable message-ID tiebreaker.
- **2026-06-10** — Same-inbound engine runs are serialized before inference and tool execution with a transaction-scoped Postgres advisory lock on a dedicated small pool. The reply unique index remains the persistence backstop. Empty/step-limited read-only turns stay retryable; if a mutation was attempted, the engine immediately persists a neutral human-verification handoff with the original usage metadata. Phase 5 uses exported `handoffFailedTurn` after final retry exhaustion.
- **2026-06-10** — Phase 3 uses AI SDK `6.0.199` with `@openrouter/ai-sdk-provider` `2.9.0`. Every OpenRouter route enforces ZDR, denied provider data collection, required parameter support, usage accounting, and same-model provider fallback. Model selection remains env-driven through `selectModel()`; there is no silent model substitution.
- **2026-06-10** — Conversation tools receive `pt_id` and `patient_id` only from validated engine context. Added `list_upcoming_appointments` for safe cancel/reschedule discovery. Appointment tools remain deterministic stubs until Phase 4; escalation is a real conversation-domain state change.

- **2026-05-22** — Embedded Signup implemented as Meta's **current JS-SDK popup flow**, diverging from the tech doc's prose (which described the legacy redirect/`state`/short→long-token model). Verified against Meta docs + ISV guides that pure-redirect OAuth can no longer deliver the inline WABA-creation experience and is incompatible with the `config_id` saved in Phase 0. Concretely: the `/settings` client runs `FB.login({ config_id, response_type:'code', override_default_response_type:true })`, captures `phone_number_id` + `waba_id` from the `WA_EMBEDDED_SIGNUP` postMessage, and POSTs `{ code, phoneNumberId, wabaId }` to `app/api/auth/meta-embedded/route.ts` (now a `POST`, not a redirect `GET`). CSRF is bound by the authenticated Supabase session + an `Origin === NEXT_PUBLIC_APP_URL` check — no signed `state` token, because there is no redirect round-trip to carry one. The code is exchanged once at `GET /<v>/oauth/access_token` for the long-lived business token (no separate short→long swap). New client env: `NEXT_PUBLIC_META_APP_ID` + `NEXT_PUBLIC_META_CONFIG_ID` (must be set in Vercel before any deploy-based test — `NEXT_PUBLIC_*` is build-time inlined, per the 2026-05-14 OAuth lesson). Updated tech doc §5.4 + the Phase 2 checklist to match.
- **2026-05-22** — Order of operations in the signup callback: exchange → register (best-effort) → `subscribed_apps` → encrypt → persist → emit. `subscribed_apps` runs before persist so it doubles as the token-validity gate (a bad token fails there, before we write a row). Phone `register` is best-effort (warn-and-continue): Embedded Signup numbers are usually pre-registered and a register failure shouldn't block a working connection. Persist goes through `getServiceClient(ptId)` (we have tenant context here, unlike the webhook). Duplicate `phone_number_id`: a new unique index (`0005_whatsapp_connection_unique`) turns a collision into a Postgres `23505`; same-PT → update the row (reconnect/token refresh), different PT → `MetaSignupError('duplicate_number')` → 409. The unique-violation check walks the error `.cause` chain because Drizzle 0.45 wraps driver errors in `DrizzleQueryError` (the SQLSTATE is on `.cause`, not the top level — caught by a failing test first).
- **2026-05-22** — Centralized Graph API access in `lib/channels/whatsapp/{constants,graph,errors}.ts`: `graphFetch` is the single choke point (sets the bearer header, parses JSON, throws typed `GraphApiError` with Meta code/subcode) used by both the signup route and the adapter; it uses global `fetch` so tests stub via `vi.stubGlobal`. `GRAPH_VERSION` pinned to `v25.0` (latest stable as of 2026-02, supported ~2 years) as a code constant, not env — bump deliberately. Token is only ever on the Authorization header; never logged (confirmed by grep audit + an automated console-spy test).
- **2026-05-22** — Channel adapter (`lib/channels/whatsapp/client.ts`) scoped to what Phase 2 acceptance needs: `sendFreeForm` (24h-window guard read from `conversations.last_inbound_at` at _send_ time), `sendTemplate` (refuses unless an `approved` `message_templates` row exists), `submitTemplate`, `getTemplateStatus`, and a shared auth-error path (401/403 → `status='revoked'` + `wa.connection.revoked`). `getQualityRating` + rate-limit/tier throttling are **deferred to Phase 5** (the docs schedule polling/throttling there). - **2026-05-22** — `bootstrapWaConnection` is the **first real Inngest function** (registry was empty). Triggered on `wa.connection.created`, it submits the shared `appointment_reminder_24h` UTILITY template (Option A — consistent wording across PTs) and writes a `pending` `message_templates` row. Idempotent: a reconnect re-emits the event, so it skips when the template row already exists rather than resubmitting to Meta. The core is a plain async fn (`bootstrapWaConnectionCore`) so it's testable without the Inngest runtime. Approval polling + `wa.template.approved` are deferred to Phase 5. `GET /api/inngest` now reports `function_count: 1`.
- **2026-05-14** — WhatsApp webhook handler at `app/api/webhooks/whatsapp/route.ts` is now production-shaped. Signature verification is a pure function in `lib/channels/whatsapp/signature.ts` (no env access — callers pass the secret); the route module captures `META_APP_SECRET` + `META_WEBHOOK_VERIFY_TOKEN` via a tiny inline `requireEnv` helper that returns `string` (TS can't narrow module-scoped optional bindings across function boundaries cleanly). Payload validation uses a zod schema in `lib/channels/whatsapp/payload.ts` that's deliberately permissive on optional fields — Meta's shape evolves. Per-message transaction does patient upsert → conversation upsert (bumping `last_inbound_at`) → idempotent message insert keyed on `external_id`; `inngest.send('message.received', ...)` fires outside the transaction so a rolled-back row never produces a phantom event, and Inngest dispatch failures degrade to a warn (a dropped event is replayable from the persisted row; a 500-to-Meta would trigger retries we don't want). Service writes go through bare `db` from `@/lib/db`, not `getServiceClient(ptId)` — the webhook has no tenant context on entry, and the `pt_id NOT NULL` schema constraint is the real safety net. Added a unique index `patients_pt_wa_id_uq` on `(pt_id, wa_id)` (plain, not partial — Postgres treats NULL as distinct, so manually-entered patients without a wa_id won't collide; partial would have required a `targetWhere` predicate that Drizzle's `onConflictDoNothing` doesn't expose) plus `whatsapp_connections_phone_number_id_idx` for the per-webhook lookup. Drizzle migrator works off `meta/_journal.json`, not folder listing — hand-authored SQL won't apply unless the journal entry exists; learned the hard way (test failure → ran `pnpm db:generate --name whatsapp_webhook_indexes` to regenerate properly).
- **2026-05-14** — Token encryption helpers in `lib/db/crypto.ts` expose a minimal two-function async API (`encryptToken` / `decryptToken`) that wraps `pgp_sym_encrypt` / `pgp_sym_decrypt` via a single SELECT round-trip each. Reason: both Phase 2 consumers (Embedded Signup writes once, channel adapter reads once per outbound send) are infrequent, so the round-trip cost is irrelevant; a composable `sql` builder would force the encryption key to leak across more call sites without a real performance win. Key is captured once at module init from `TOKEN_ENCRYPTION_KEY` (matching the repo's "throw at construction" pattern); no per-call env read and no runtime rotation, because silent drift between calls would be a much worse failure mode than a deploy-time restart. No length / format validation on the key — `pgp_sym_encrypt` accepts any non-empty string and derives its own internal key. Schema column `whatsapp_connections.access_token_encrypted` was already `bytea` from `0001_init_schema.sql`, so no migration. Round-trip integration test against the local Postgres confirms encrypt → decrypt yields the original plaintext and that successive encryptions of the same input produce different ciphertexts (pinning the non-deterministic property so a later refactor to a deterministic mode would fail loudly).
- **2026-05-14** — Inngest client is a module-level singleton in `lib/inngest/client.ts`, not a per-call factory like `lib/supabase/*`. Reason: the Inngest client carries no per-request state (no cookies, no RLS context); the canonical SDK pattern (per `node_modules/inngest/components/Inngest.d.ts`) is module-level instantiation, and a factory would only add ceremony. App `id` is fixed at `'medium'` and treated as immutable — changing the id orphans Inngest history. `INNGEST_EVENT_KEY` is validated at module init (matching the repo's "throw at construction" pattern for env vars); `INNGEST_SIGNING_KEY` is intentionally validated lazily inside `serve()` because the Inngest dev server bypasses signature verification locally and a boot-time throw would block `pnpm dev`. `.env.test` carries `INNGEST_EVENT_KEY=dev` so any future test that imports the client transitively can run without the production key.
